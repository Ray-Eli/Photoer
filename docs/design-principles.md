# 设计原则

本文记录 Photoer 项目的通用设计原则，适用于所有模块。

## 一、安全优先

### 1.1 不泄露账号存在性

任何接口都不能让外界推断"某个邮箱/用户名是否已注册"。

- 注册时邮箱已存在 → 页面正常显示"验证码已发送"，通过邮件告知真实情况
- 登录失败 → 统一提示"账号或密码错误"，不区分账号不存在和密码错误
- 忘记密码时邮箱不存在 → 页面表现一致，发邮件说明
- 注销用户重新注册 → 页面表现一致，发邮件说明冷却期

**例外**：密码验证通过后，可以明确提示账号被封禁及原因。因为攻击者需要先知道正确密码，泄露风险极低。

### 1.2 验证顺序：便宜的检查在前

按成本从低到高排列检查步骤，让攻击流量在最便宜的环节被挡住。

- IP 限流 （查 Redis 计数，几乎零成本）
- 人机验证 （调用第三方 API，有网络开销和额度消耗）
- 数据库查询 （查库 + bcrypt 比对，CPU 密集）

### 1.3 唯一性约束必须用数据库索引

应用层的"先查询再插入"在并发场景下有漏洞：两个请求可能同时查到"不存在"，然后都插入成功。

数据库唯一索引的检查是原子的，并发安全。应用层校验只用于提供友好的错误提示，不能替代数据库约束。

### 1.4 前后端双重校验

前端校验为了体验（实时反馈），后端校验为了安全（前端可被绕过）。两者都要有。

### 1.5 重定向白名单

`redirect` 参数只允许站内路径，拒绝 `http://`、`https://`、`//` 开头的值，防止开放重定向攻击。

## 二、策略与机制分离

机制（怎么执行）写在代码里，策略（用什么规则）放在配置或数据里。

### 2.1 判断标准

| 问题 | 是 → 配置 | 否 → 写死 |
|---|---|---|
| 这个值未来大概率会变吗 | 冷却期天数、限流阈值 | 密码用 bcrypt 加密 |
| 变更成本高吗（需重新部署、影响用户） | Session 时长 | — |
| 需要针对个案破例吗 | 单个用户名永久锁定 | — |

### 2.2 配置的三个层次

| 层次 | 适用 | 当前选择 |
|---|---|---|
| 环境变量 `.env.<环境>` | 不同环境值不同（数据库地址、密钥） | 已使用，见 decisions.md ADR-011 |
| 配置文件 `src/config.js` | 业务规则，改动进 Git 有记录 | **当前采用** |
| 数据库配置表 | 需运行时动态调整，配合运营后台 | 以后引入 |

### 2.3 避免过度配置化

不是所有东西都该可配置。过度配置会导致：读代码看不出实际行为、配置项无人维护、测试组合爆炸。

## 三、当前状态与历史记录分表

需要保留变更历史的字段，采用"当前状态表 + 历史记录表"的模式：

- 当前表只存有效数据，可以加唯一索引
- 历史表只存已失效数据，允许重复
- 变更时在事务中完成"归档旧值 + 更新新值"

已应用于：`user_identities` / `identity_history`、`users.username` / `username_history`

**不这样做的后果**：历史记录和当前数据混在一张表，唯一索引会冲突。

## 四、数据存储分层

| 数据类型 | 存储 | 理由 |
|---|---|---|
| 业务数据、关系 | MySQL | 需要关联查询、事务 |
| 图片、视频文件 | 对象存储 OSS | 大文件，需 CDN 分发。**绝不存进数据库** |
| 会话、验证码、限流计数 | Redis | 有时效、访问频繁、丢失不致命 |
| 应用运行日志 | 文件 | 量大、只按时间查、不参与业务逻辑 |

## 五、部署环境只读

服务器上的代码目录不接受任何本地修改，一切以 Git 仓库为准。

- 部署脚本执行 `git checkout .` 丢弃本地改动
- 依赖安装用 `npm ci`（严格按 lock 文件，不改写它）
- 统一用 `www` 用户操作，避免与 root 产生权限冲突

**这条原则的价值**：杜绝"服务器上的代码和仓库不一致"这类难以排查的问题。

## 六、接口设计客户端无关

后端只提供 JSON API，不混入页面渲染逻辑。这样同一套接口可以同时服务 Web、未来的 App 或小程序。

同一个接口在登录和未登录状态下可以返回不同数据（如是否已点赞），但不应该有两套接口。

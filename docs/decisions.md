## ADR-001：产品形态定位为 Web 应用

**日期**：2026-08-21

**背景**：考虑过 App、微信小程序、Web 三种形态。

**决策**：Web 应用，响应式（桌面优先，移动端可用）。

**理由**：
- 目标用户是专业摄影师，工作流是"相机 → 电脑修图 → 发布"，终点在桌面
- 拍摄地推荐功能需要地图和详细信息，大屏体验更好
- 个人开发者身份：小程序内容社区类目需要企业主体；App 上架需要资质和费用
- Web 无备案、无审核门槛，能最快跑通完整产品闭环
- 后端接口可复用，以后转 App/小程序不浪费

**代价**：放弃了 App 的推送能力和更好的图片浏览性能。

**未来路径**：Web → PWA → 套壳 App → 核心页面原生化

## ADR-002：允许游客浏览内容

**日期**：2026-08-21

**背景**：曾考虑强制登录以简化状态管理。

**决策**：游客可浏览内容，操作（点赞、评论、关注）时才要求登录。

**理由**：
- 搜索引擎爬虫是游客，不让游客访问等于放弃自然流量
- 分享链接给未注册用户，打开是登录页会中断传播
- 新用户需要先看到内容价值才有注册动机
- Instagram、Twitter 都是这个模式（Twitter 2023 年曾关闭游客访问，两周后恢复）

**代价**：需要处理"游客/登录"两种状态，接口要区分公开数据和权限数据。

## ADR-003：用 Session 而非 JWT

**日期**：2026-08-21

**背景**：初版代码使用 JWT。

**决策**：改用 Session + Redis + HttpOnly Cookie。

**理由**：产品需求中有四项与 JWT 特性冲突：

| 需求 | JWT | Session |
|---|---|---|
| 闲置超时自动退出 | 签发后有效期固定，无法调整 | 天然支持 |
| 记录最后活跃时间 | 需额外写库，抵消无状态优势 | 本就在查 |
| 立即强制下线 | token 已发出，无法撤销 | 删记录即可 |
| 封禁账号 | 同上 | 同上 |

JWT 的优势（服务器无状态、多服务器、开放 API）在当前单服务器单应用场景下均用不上。

**代价**：需要 Redis 存储会话数据。

**备注**：若坚持 JWT 并补上这些能力，最终会演变成"每次请求查库验证 token 状态"，本质上就是 Session，只是多了一层复杂度。

## ADR-004：存储位置选 HttpOnly Cookie

**日期**：2026-08-21

**决策**：Session ID 存于 HttpOnly Cookie，配合 SameSite 属性。

**理由**：

| 攻击 | localStorage | HttpOnly Cookie |
|---|---|---|
| XSS（恶意 JS 执行） | JS 可直接读取 token | JS 无法读取 |
| CSRF（跨站请求伪造） | 无风险 | 有风险，但 SameSite 可防 |

XSS 危害更大（一旦得手能做的远不止盗 token），且 CSRF 有成熟防护手段。

## ADR-005：用户标识采用双 ID 方案

**日期**：2026-08-21

**决策**：
- `id` BIGINT 自增：数据库主键，内部关联使用
- `public_id` CHAR(21) NanoID：对外暴露的稳定标识
- `username`：URL 与登录使用，可变

**理由**：
- 纯自增 ID 可被枚举（遍历所有用户）、泄露业务规模（注册序号暴露用户总量）
- 纯 UUID 作主键有索引碎片问题（UUID v7 已改善，但仍有存储开销）
- 双 ID 兼顾内部性能与外部安全

**代价**：代码中需处理两套 ID 的转换，有误将内部 id 暴露的风险。

**纪律**：内部 `id` 永不出现在 API 响应、URL 或前端代码中。

## ADR-006：邮箱验证用验证码而非激活链接

**日期**：2026-08-21

**背景**：两种方案各有优劣，讨论后改选验证码。

| | 激活链接 | 验证码 |
|---|---|---|
| 多标签同步 | 有问题 | 无 |
| 关闭页面 | 无影响（状态在邮件里） | 流程中断 |
| 暴力破解 | 无风险（长随机 token） | 需限制尝试次数 |
| 跨设备 | 较顺 | 需手动抄写 |

**决策**：验证码。

**理由**：流程连续，用户始终在同一页面；且为 v2 的手机号验证提前建立机制。

**代价**：需要处理"关闭页面流程中断"的问题，通过独立路由 + URL 临时标识实现刷新恢复。

## ADR-007：用户名劫持防护

**日期**：2026-08-21

**背景**：用户名可改且唯一，改名后旧名字若立即释放，会被他人抢注冒充。

**决策**：
- 冷却期 90 天，期间他人不可占用，原主人可改回
- 改名频率限制：一年 2 次，按滚动 365 天窗口计算（不是自然年），查 `username_history.created_at`；第一次把自动生成的默认用户名改成自定义名字，同样计入这个次数——注册时生成的默认用户名本质上也是"一次占用"，不区分对待会让"首次自定义"变成不受限制的额外一次改名机会
- 改回自己曾经使用过的旧用户名，同样计入改名次数，不作为免费的撤销操作——否则用户可以在两个自己拥有过的名字之间无限横跳，实质上绕开了一年 2 次的限制
- 支持单条记录永久锁定（应对有影响力账号）
- URL 使用 username，改名后旧链接 404（不跳转，不透露改名信息）

**曾考虑但否决**：永久锁定所有用过的用户名。因会持续消耗用户名池（改名越多浪费越大）、僵尸账号锁死好名字、且给恶意抢注提供牟利空间。

## ADR-008：注销采用软删除

**日期**：2026-08-21

**背景**：曾考虑归档表方案（数据搬到 deleted_users 表）。

**决策**：软删除，数据全部保留在原表，仅标记 `status='deleted'`。

**理由**：注销用户的历史内容需要保留，且其他用户的评论区要显示"该用户已注销"。若搬走数据，所有外键关联会断裂。

**规则**：
- 注销后立即踢下线，不可登录，不可撤销
- 30 天内邮箱和用户名不可被他人使用
- 30 天后：username 改为 `{原名}_deleted_{id}`，user_identities 中的邮箱记录删除（历史保留在 identity_history）
- 30 天清理完成后，原邮箱和原用户名即被释放，任何人（包括原账号本人）都可以重新注册使用，本人没有优先权——清理任务执行后，系统已经无法区分"新申请者是原账号本人"还是"完全无关的第三方"，也不需要区分，统一按全新注册处理
- 用户的照片、评论等数据永久保留

## ADR-009：登录凭证独立建表

**日期**：2026-08-21

**背景**：v1 只支持邮箱登录，曾考虑直接放 users 表。

**决策**：独立 `user_identities` 表。

**理由**：v2 规划中要加入手机号登录，且需保留邮箱换绑历史。若放 users 表，每加一种登录方式就要加列 + 加一张历史表；identities 表只需加一行数据。

**代价**：登录查询需要一次 join。

## ADR-010：接口文档仅本地开发环境暴露

**日期**：2026-08-30

**背景**：接入 Swagger/OpenAPI 接口文档（swagger-jsdoc 生成规范 + Scalar 渲染页面，最初用 swagger-ui-express 渲染，后替换为 Scalar，规范生成这一层没有变化），需要确定文档页面在测试服、正式服上的可见性。

**决策**：
- 只有 `NODE_ENV` 显式等于 `development` 时才挂载 `/api-docs` 路由，其余情况（包括 `NODE_ENV` 未设置）一律不挂载
- 未挂载时访问该路径返回标准 404，不返回 403 或其他"无权限"类响应

**理由**：
- 判断逻辑用白名单而非黑名单：白名单写法（"只有等于 development 才开启"）在环境变量缺失时默认关闭，黑名单写法（"只要不等于 production 就开启"）在同样情况下默认开启。安全相关的判断应该在配置缺失时失败到安全的一侧，而不是失败到暴露的一侧。正式服部署方式尚未落地（见下方技术债清单），后续用宝塔等工具配置进程时存在忘记设置 `NODE_ENV` 的可能，白名单写法能兜住这种情况
- 用 404 而非 403：403 相当于告诉对方"这个资源确实存在，只是你没有权限访问"，本身就泄露了资源存在性，跟 design-principles.md 1.1 条"不泄露账号存在性"是同一个原则的延伸——不注册路由、让请求落到 Express 默认的 404，是唯一不会泄露信息的做法

**代价**：本地开发必须显式设置 `NODE_ENV=development` 才能看到文档（`package.json` 的 `start` 脚本已经这样配置）；如果本地用别的方式启动服务（不经过 `npm start`）又没有自己设置这个环境变量，文档也会被一并关闭。

## 已知问题 / 技术债

记录已经发现、但暂时不处理的问题，避免遗忘。

- **生产环境部署方式尚未落地**：Nginx 反代、pm2 常驻、HTTPS 证书配置目前都只停留在讨论阶段，仓库里没有任何对应的部署脚本/配置文件。计划等域名 ICP 备案完成后再启动。
- **`.env` 里的 `JWT_SECRET` 是遗留字段**：认证方案已经从 JWT 改为 Session（ADR-003），代码中已不再使用 `jsonwebtoken`，这个配置项可以清理掉。
- **根路径 `GET /` 返回的是开发早期留下的提示文案**：`src/index.js` 里 `GET /` 目前返回中文提示"Hello, 服务器已经跑起来了！"，这个响应在生产环境同样存在，会向访问者确认"这里有一个活着的服务"，且不够专业。等做生产环境部署配置时一并处理——可选方案是改成标准的健康检查响应（如 `{"status":"ok"}`），或直接移除让其返回 404。
